# 证据选择实验：首轮结果与下一步

2026-11-12。状态：代码实现、30 题 × 5 配置的生成、统一格式的 150 次评分均已完成。归档结果已取回并核对远端哈希。本报告附有[数值结果与逐题配对差异](selection-pilot-metrics.json)及[固定查询样本](selection-pilot-sample.jsonl)。

## 实验设置与复现

从 350 条 practice 查询中排除此前查看过的前五条，对其余 ID 按 SHA256(seed + ':' + query_id) 排序取前 30 条。种子为 `2026-11-12-evidence-audit-v1`；选择发生在检查其检索和答案结果之前。这是探索样本，不是独立确认集。使用冻结 ASR 转写、enc_a 的原始精确检索 top-100 候选，选择代码不读取 qrels；生成和评价均使用 `utter-project/EuroLLM-22B-Instruct-2512`，温度分别为 0.1 和 0.0。

重排序模型为 `cross-encoder/ms-marco-MiniLM-L6-v2`，revision `233902d25c440f23af6f7d6e94d2946bac0bee0a`；使用原始 logits 降序排列，同分保持原排名，batch size 16，最大配对长度 512，只截断文档。tokenizer 来自生成模型官方仓库，revision `8c6ed5c8d18527d9daed994f645032b86c53f0bb`。输入预算包含系统提示、问题、文档标签和生成前缀；按文档排名依次取内容，最后一篇可截断，之后停止。每题内五种配置按种子 `2026-11-12-selection-pilot-v1` 与 query ID 决定的顺序打乱；每个答案生成和评分各一次。

评价使用课程 `rag-answer-rubric-v0.1` 的原始问题、参考证据和严格分数解析。由于默认文本模式曾连续返回非法 JSON，本轮五组统一请求 JSON-object 输出，使用单独缓存；默认模式的部分评分不混入比较。格式约束不保证评价正确。一个早期 token 计数错误的试运行也完全排除；修正后的全部上下文与答案均重新生成。

环境为 Python 3.11.18、PyTorch 2.10.0+cpu、NumPy 2.4.6、sentence-transformers 6.3.0。运行与汇总命令见[扩展模块说明](../extensions/README.md)。服务器模型版本和随机种子不可控，重新调用不保证答案完全相同。

## 当前结论

**这批 practice 样本没有显示所选 100 候选重排序器的优势。** 直接增加上下文提高了标注覆盖；同等输入预算下，重排序的标注覆盖与自动分数均较低。我们同时发现裁判会误读或选择性使用参考证据，因此不能仅凭这些自动分数宣称某个配置的真实答案质量更好。

这是采用现有方法后得到的受控探索结果，尚非最终方法选择或 dev 验证。没有使用 dev，也没有在读到答案后更换这 30 条样本。

## 做了哪些技术改动

- [证据选择模块](../extensions/evidence_selection.py)：保留原始 top-k 提示词，增加完整聊天输入的 token 预算、按排名前缀取文档、最后一篇截断和截断记录。
- [实验运行器](../extensions/run_selection_experiment.py)：复用固定转写及 top-100 候选，加入 MiniLM-L6 重排序，冻结逐题上下文，并支持严格校验后的生成续跑。选择过程不读取 qrels。
- [生成器](../src/generator.py)：请求内容与温度不变，增加服务端 token 用量、实际响应模型及完成原因记录。
- [评价器](../scripts/evaluate_answers.py)：默认请求保持原样；新增可选 JSON 输出模式、独立缓存命名与原始输出保存，解决本轮裁判返回非法 JSON 的问题。
- [汇总工具](../extensions/summarize_selection_experiment.py)：检查配对覆盖、实际预算、选中文档覆盖、成本来源及逐题评分变化。

本地 12 项测试通过。计算节点验证了原始 top-5 提示词一致、预算控制和评价请求协议；独立复算 30 个重排序分数，最大绝对误差约 0.0000012，分数方向校验通过。

## 五组比较

以下均为同一批 30 条查询。标注覆盖是 selected-ID macro Recall，不等同于证据充分性；自动答案分数为正确性、依据性、完整性总分除以 12。

- **原始 top-5**：平均输入 **1297.4 tokens**；标注覆盖 **0.2883**；自动答案分数 **0.3056**。
- **原始 top-20**：平均输入 **4846.6 tokens**；标注覆盖 **0.5064**；自动答案分数 **0.3389**。
- **重排序后 top-5**：平均输入 **1375.8 tokens**；标注覆盖 **0.2717**；自动答案分数 **0.2889**。
- **原始排序，4096-token 预算**：平均输入 **4096.0 tokens**；标注覆盖 **0.4664**；自动答案分数 **0.3750**。
- **重排序，4096-token 预算**：平均输入 **4095.8 tokens**；标注覆盖 **0.4164**；自动答案分数 **0.3028**。

全部 150 个答案正常结束；150 条服务端输入计数与本地计数逐条一致；没有预算超限。原始 top-5 的 30 份提示词与原始 context builder 完全一致。

预算方法都允许最后一篇截断，两个预算组各有 29 题实际截断一篇文档。重排序预算组若只计完整保留的正标注文档，覆盖率为 **0.3998**，低于其 selected-ID 覆盖率 0.4164。命中文档 ID 不能证明关键句保留下来。

## 配对变化与不确定性

- top-20 减 top-5：平均自动分差 **+0.0333**；6 题提高、19 题持平、5 题降低；query bootstrap 95% 区间 **[-0.0583, 0.1333]**。
- 重排序 top-5 减原始 top-5：平均分差 **-0.0167**；7 题提高、15 题持平、8 题降低；区间 **[-0.1000, 0.0694]**。
- 同预算重排序减原始排序：平均分差 **-0.0722**；5 题提高、15 题持平、10 题降低；区间 **[-0.1583, 0.0139]**。

所有区间均包含零。它们只描述这批查询的重采样变化，不包含重复生成、重复裁判、系统性误判或方法选择造成的不确定性。不能把最高均分 0.3750 当作已证实的最优方案。

## 成本能说明什么

top-20 输入约为 top-5 的 **3.74 倍**。这是真实返回的 token 用量比较，不是运行时间或货币成本的倍数。

本轮原始 top-5、top-20、重排序 top-5 的远端生成延迟中位数分别约为 **4.03、4.23、2.93 秒**；两个预算组约为 **4.55、4.55 秒**。这些是单次 API 观测，输出长度与服务负载也不同，不据此声称稳定加速。

重排序 100 个候选在 `opencast` 的 2 CPU 分配上平均约 **26.20 秒/题**。生成与上下文准备在 `saxa` 上完成，分数及原始推理成本来自前一作业的有效重排序缓存。二者相加是归属成本估计，并非单节点实测端到端延迟。正式性能结论需要同节点、预热和重复测量；不能推广成 GPU 或所有 CPU 上的重排序成本。

## 具体案例提供了哪些解释

**CAGR 发音题：确实丢失了已检索到的证据。** 原始排名前两篇是“与 bagger 押韵”和“应逐字母读”的资料，重排序后降至 11 和 38。它们与问题配对后分别仅 34 和 97 tokens，没有被 512-token 限制截断。原始 top-5 答案选择逐字母读，受其中一篇支持；重排序 top-5 答案表示证据没有发音信息。这个信息损失不能仅用“长文档截断”解释。与此同时，裁判把原始答案判为零分，声称参考明确排除 initialism，忽略参考中恰好有一篇明确持该观点。

**期权估值题：增加上下文带入了具体方法。** 标注资料原始排在第 11，完整讨论二项式定价、风险中性估值和对冲。top-20 答案加入这些内容；top-5 答案则混入一般投资估值和心理素质，重排序 top-5 也没有覆盖同样的方法。自动分数从 top-5 的 0 到 top-20 的 1，与内容变化方向一致，但不能据此认为每个财务细节均已独立核实。

**信用评分题：qrels 与裁判均需谨慎使用。** 原始 top-5 没有正标注，却包含直接回答如何使用信用卡的资料。参考组中既有反对使用信用卡的意见，也有支持有纪律使用的建议；裁判对原始答案的零分理由只采用前者。这里不能用“未命中标注”推出“没有有用证据”，也不能把意见冲突自动变成回答错误。

上述为有目的的助手文本核查，未估计代表性人工错误率；没有重写自动分数，也不构成现实金融建议。

## 事后诊断：候选更深是否总是更好

利用已保存的逐文档分数，从原始前 20、50、100 候选中分别选重排序 top-5，平均标注覆盖为 **0.3117、0.2883、0.2717**。计算没有调用新模型或 API，也没有测量新延迟。原始 top-5 为 0.2883。

这是结果出来后的探索：[逐题诊断](selection-candidate-depth-diagnostic.json)。它提示较大候选池可能给不完美的排序器引入更多误排机会；并未证明原因，也没有证明前 20 候选的答案质量或成本优势。

**下一轮优先检验候选深度，而非直接扩大实验到 dev。** 用同一排序器比较较小与较大候选池，核查哪些资料被错误提升或压低，并配合可靠的答案检查。在同一节点测量成本。必要时单独检验 ASR 转写中的缩写拼写和评分器长文档截断，避免一次改变多个组件。
