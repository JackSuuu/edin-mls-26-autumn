Component Choices, Quality and Cost in CUDA ASR and
RAG
Anonymous authors
Paper under double-blind review
1 Introduction
How do component choices affect final quality and computational cost? We investigate this
question through custom CUDA kernels for GLM-ASR-Nano and a retrieval-augmented
generation (RAG) pipelineLewis et al.(2020). The ASR baseline uses PyTorch fallbacks
(./run.sh –cuda none); our four CUDA task groups pass the supplied tests, but their GEMM
bottleneck makes full execution slower.
For RAG, the hypothesis is that selecting more useful evidence from an existing candidate
pool can improve answers without greatly increasing generation context. An initial five-arm
study covers 350 practice and 125 held-out dev queries: more context raises coverage without
a detectable answer-score gain, while MiniLM reranking loses coverage. Candidate-pool and
L12 controls locate a selector limitation. An exploratory Qwen extension improves practice
ranking and paired answer scores at substantial cost. A subsequent frozen-configuration
check on the previously inspected dev set replicates retrieval gains, but its positive mean
answer-score difference remains uncertain. Dev is not used to retune Qwen; this is not a
newly collected or untouched independent test.
The selected ASR answers are Task 1, Question 1 (Section4.4), Task 2, Question 3 (Sec-
tion 4.5), Task 3, Question 2 (Section4.6), and Task 4, Question 1 (Section4.7). The
Appendix maps measurements to committed evidence files.
2 System and Technical Approach
2.1 Supplied baseline
The homework provides csrc/task*.cu with numbered blanks, launch_* grid configuration,
CPU references in tests/, and glm_asr_cuda/ops.py which selects CUDA or PyTorch per
kernel group.
2.2 Task 1: RoPE kernel design
RoPE rotates pairs (v[i], v[i + h]) before attention, with h = rotary _dim/2: ∠ = pos ·
inv_freq[i], v[i]′ = a cos ∠ − b sin ∠, v[i + h]′ = b cos ∠ + a sin ∠. One launch covers both q
and k: threads 0, . . . ,q_pairs − 1 touch q, then k. Each thread maps a global pair index
to row, pair index i, and token positionpos = (row /num_heads) mod seq_len. Elements
beyond rotary_dim are untouched (audio encoder uses rotary_dim= 32 of head_dim= 64).
Implementation choices: ROPE_THREADS= 256 blocks sized by ceil(total_pairs / 256);
in-place updates; cosf/sinf computed per pair (no lookup table). Blanks 1.1–1.4 implement
indexing and the rotation; launch_rope is unchanged.
2.3 Task 2: warp/block reductions, RMSNorm, softmax
Part A (task2_reduce.cuh) implements warp_reduce_sum/max with __shfl_xor_sync
and block_reduce_sum/max via a partial[] staging buffer and two barriers. Part B builds
rmsnorm_kernel (row-wise RMS scale with learned weights) and softmax_kernel using the
online MaxSum merge from the guide: one statistics pass followed by an output pass. Task 4
reuses the warp helpers for tile-wise probability sums.

2.4 Task 3: shared-memory tiled GEMM
Following the lecture tiled GEMM, each 16 × 16 thread block computes a tile of y =
GELU(xW ⊤ + b) with TILE=16, loading x and transposed W into __shared__ buffers
each K-step. Padding ws with [TILE][TILE+1] avoids bank conflicts; out-of-bounds loads
use zero so every thread hits both __syncthreads() calls.
2.5 Task 4: tiled attention with online softmax
Each block covers ATTN_WARPS=4 queries of one head; each warp streams keys/values in
tiles of 32 through dynamic shared memory (k_tile, v_tile, cached scaled queries). Running
statistics (m, ℓ, acc) implement FlashAttention-style online softmaxDao et al.(2022) with
correction corr = exp( m − mnew) when a tile raises the max. Causal masking sets scores
to −∞ past last_key; GQA maps kv_h = h / (num_heads/num_kv_heads). Blank 4.5
must broadcast each lane’s probability with __shfl_sync so every lane accumulates∑r prvr
across all keys in the tile (not only its own lane).
3 Experimental Methodology
3.1 ASR kernels
Hardware: NVIDIA RTX A6000 (sm_86, 84 SMs; test harness reports 768 GB/s peak
DRAM bandwidth). Software: mls-asr conda environment, CUDA via /usr/local/cuda,
repository hw1-asr.
Quality metrics: per-case max_err against CPU references (make test1–4) and transcription
string match on test_audio.wav (./run.sh with all CUDA kernel groups). Cost metrics: per-
kernellatency/GFLOP/sfromtestsandend-to-endms/tokenwith–profileshares. Controls:
same GPU for sweeps, rebuild with make clean when changing NVCCFLAGS, default -O3
-std=c++17 -lineinfo -diag-suppress 177. All reported ASR measurements use the fresh
default build on otherwise idle GPU 1; analytical memory counts below are derived from
the committed kernel code and test shapes.
3.2 RAG evidence-selection study
System: practice/dev audio questions → ASR transcript → query encoding → retrieval
over 24,000 enc_a document vectors→ evidence selection/context construction → ELM
answer generation (utter-project/EuroLLM-22B-Instruct-2512, temperature 0.1). Retrieval
uses exact cosine similarity with saved transcripts to isolate downstream changes.
Initial paired evaluation: on 350 practice and 125 held-out dev queries we compare five
configurations using the same transcripts, corpus, model and prompting: dense5 (top-
5), dense20 (top-20), rerank5 (cross-encoder reranked top-5 Nogueira & Cho (2019)),
dense_budget (dense fill to ∼4096 input tokens), and rerank_budget (reranked fill to
∼4096). We report automatic judge scores (correctness, grounding, completeness in[0, 4],
summed and divided by 12), selected-ID qrel recall, input tokens and median generation
latency. Initial score intervals use 5,000 paired query-bootstrap resamples.
Exploratory selector extension: Qwen3-Reranker-0.6B/4B reorder frozen top-100 candidates
on all 350 practice queries. The primary matched arm receives the original-character docu-
ment prefix visible under MiniLM’s 512-token pair limit, with no additional Qwen trunca-
tion; thesecondaryarmallows2048Qwentokensincludingitstemplate. Oﬀicialinstructions
and descending yes minus no logits are fixed. Qwen uses BF16, MiniLM float32; tokenizers,
architectures and training also differ, so this is not a size-only ablation. The Qwen phase
has its own frozen dense ranking cache.
Fresh paired answers and frozen dev check: fresh dense5 and qwen4_matched5 answers
use the same generator, temperature, prompt and five full-text records, without truncation;
only records/order differ. Arm execution order is shuffled per question. One generation and
one JSON-mode judge call are made per answer; Qwen intervals use 2,000 paired query re-

4 Results and Analysis
4.1 RAG: initial evidence quantity and selection
The practice retrieval baseline has Recall@5 of 0.421 versus Recall@100 of 0.770 (350 queries;
baseline-3713067.md). This gap indicates that relevant documents often occur below the
initial evidence cutoff, motivating evidence selection from a deeper candidate pool under a
limited context budget. The initial practice/dev study uses enc_a embeddingsReimers &
Gurevych (2019) and ELM EuroLLMMartins et al.(2024); its full table is in AppendixC.
Quantity is not suﬀicient. Every reported paired answer-score interval in the initial five-
arm study includes zero (AppendixC). On dev, increasing from five to twenty documents
raises recall from 0.379 to 0.580 but not mean answer score: ∆ = 0 .0000, 95% interval
[−0.0440, 0.0427]. The budget-reranking difference of −0.0447 [ −0.1007, 0.0133] on dev is
−0.0069 [ −0.0390, 0.0255] on practice. Within dev arms, recall still correlates with score
(r = 0.294–0.465). Budget arms use less input than dense20 (4096 versus 4948 tokens). Gen-
eration medians avoid API outlier distortion; the dev dense-budget maximum is 186,750 ms.
These observations do not identify whether extra evidence is redundant, poorly used by the
generator, or obscured by judge noise.
Candidate-pool ablation. On 350 practice questions, GPU cross-encoder pools of 20/50/100
yield Recall@5 of 0.411/0.399/0.388, below dense’s 0.421; mean costs are 39/97/194 ms. L6
removes 83 qrel-positive document pairs from dense’s first five while adding 47. Increasing
the candidate count therefore does not fix this selector. Dev reranking’s 262 ms is on GPU;
the pilot’s 26 s/query is on two CPU cores, not a matched speed comparison. BM25/RRF
dev Recall@5 of 0.208/0.303 is below dense’s 0.379, without an answer-quality comparison.
L12 control. A matched practice-only L6/L12 rerun exactly reproduces the old L6 scores.
L12 improves Recall@5 by 0.0225[0.0022, 0.0427] over L6, but not demonstrably over dense:
−0.0111 [ −0.0427, 0.0201]. Median reranking grows from 169 to 296 ms without a de-
tectable MRR/NDCG gain over L6. It removes 67 and adds 42 relevant pairs relative to
dense: fewer losses, not more recoveries in pair counts, which are not a macro-recall de-
composition. This points to selection quality, not just candidate quantity, as a possible
bottleneck (AppendixD).

4.3 ASR correctness and end-to-end findings
All four task suites report ALL PASS. All-CUDA, Task-1-only and PyTorch-only runs repro-
duce Concord returned to its place amidst the tents. with the harness reporting 100.0% word
accuracy on this reference clip. Their measured transcription times are respectively 1986.1,
483.1 and 521.3 ms. Thus all-CUDA execution takes about3.8× as long as the PyTorch
baseline (1986.1/521.3), and is also slower than enabling only Task 1. The all-CUDA profile
attributes 83.8% to linear and 15.4% to attention; encoder attention tests report 8.641 ms
and 1333 GFLOP/s. The GEMM gap below identifies a concrete bottleneck rather than
assuming that custom kernels must outperform library-backed PyTorch.

4.4 Task 1, Question 1
For the audio encoder case, how many bytes does the kernel read and write
in total? Which fraction of your GPU’s peak bandwidth did you reach?
Theharnesscountsbytesmovedas 2·(q_rows+k_rows)·rotary_dim·4(read +writeoverthe
rotated prefix). For the audio-encoder case (B=1, seq=1500, Hq=Hk=20, rotary_dim=32),
q_rows=k_rows=30,000, so 2 · 60,000 · 32 · 4 = 15 .36 × 106 bytes (∼14.6 MiB) per call (an
analytical count, not a new timing measurement). The fresh harness reports 0.026 ms and
600.0 GB/s, 78% of the quoted 768 GB/s peak—a roofline-styleWilliams et al.(2009) check
consistent with a memory-bound kernel that also executes trigonometry and indexing.
4.5 Task 2, Question 3
How many times does your softmax read each element of x from global
memory? How many times does the textbook version (max, then sum,
then write) read it?
Our softmax reads each element twice: the first loop in softmax_kernel merges MaxSum
statistics; the final output loop rereads xr[c] to compute its normalised exponential. The
textbook implementation reads it three times, once each for maximum, exponential sum,
and output. Online softmax merges the first two passes, but does not remove the output
pass. These are source-level global-load requests, not measured DRAM transactions; cache
hits can reduce actual DRAM traﬀic.
4.6 Task 3, Question 2
Your kernel reaches only a fraction of cuBLAS’s speed on the large cases.
Name one thing cuBLAS does differently that explains part of the gap. You
do not have to implement it.
A plausible explanation is that cuBLAS likely uses more sophisticated hierarchical tiling and
register-level reuse, computing multiple outputs per thread rather than our single-output
16×16shared-memory tile. Such strategies increase reuse and arithmetic intensity; however,
cuBLAS is closed-source and we did not inspect the particular kernel dispatched here. Our
encoder q_proj reaches 2967 GFLOP/s versus cuBLAS’s 20305; fc1 + GELU reaches 2870
versus 21346 GFLOP/s. The comparison is not a pure epilogue match (our fc1 fuses GELU),

4.7 Task 4, Question 1
How much memory would the full score matrix of one encoder layer take
(20 heads, 1500 x 1500, float32)? How much shared memory does one block
of your kernel use instead?
The full score matrix takes 20 · 1500 · 1500 · 4 = 180 ,000,000 bytes (171.66 MiB). In
launch_attention, shared memory is allocated as 4[32(d + 1) + 32 d + 4d] bytes: padded
keys, values and cached scaled queries. For encoder head dimension d = 64 , this is
4[32 · 65 + 32 · 64 + 4 · 64] = 17 ,536 bytes (17.125 KiB) per block, not 48 KiB. The lat-
ter is only the launcher’s threshold for requesting an opt-in shared-memory limit. Scores
are reduced tile by tile with online softmax rather than storing the full matrix; these memory
footprints are analytical counts from the source.
5 Discussion and Conclusion
Correctness versus performance. All CUDA tasks pass, yet the custom GEMM bottleneck
makes full ASR take 1986.1 ms versus PyTorch’s 521.3 ms, about3.8× the latency. Correct
implementation alone does not establish system acceleration; profiling and library compar-
isons locate the cost.
Quantity versus selection quality. Answer-score intervals include zero in the initial five-arm
comparisons, not in every subsequent experiment. More documents and larger MiniLM
candidate pools do not solve evidence selection. Matched-text Qwen improves practice
answer scores without expanding average generation context, at substantial cost. Retrieval
gains replicate on the inspected dev set; its answer-score mean moves in the same direction
but its interval includes zero. Evidence for a downstream benefit is stronger on practice
than on dev, not a universal claim that bigger selectors help.
When is the cost justified? The added attributed delay may be problematic for interactive
voice use, whereas offline QA may tolerate it for the observed score gain. Neither a user
latency target nor a quality-to-delay utility was measured, so no configuration is universally
preferable. Qwen 0.6B is a lower-cost retrieval option, not an established better end-to-end
trade-off: its downstream answers were not evaluated.
Limits of the evidence. Qwen was selected on practice and then frozen for a new run on the
previously inspected dev set, not an untouched independent test. Genuine independent val-
idation still requires unused queries. Unadjusted query bootstrap excludes adaptive model
selection and repeated-generation/judge uncertainty. Qrels can be incomplete; selected-
ID recall can credit a truncated document without its useful span. Same-model genera-
tion/judging and observed judge inconsistencies limit quality claims. Changing checkpoints
does not identify capacity, domain mismatch, missing document background or ASR for-
matting as the root cause. ASR correctness covers supplied tests and a reference clip, not
exhaustive transcription accuracy; cost measurements do not provide a matched audio-to-
answer benchmark.
Conclusion. Component choice changes both final quality and cost. Our experiments locate
a CUDA performance bottleneck and an evidence-selection limitation. Qwen retrieval gains
persist on dev, while downstream evidence is positive on practice and uncertain on dev, with
substantialaddedcost. Optimisationshouldtarget finalqualityandlatency, notcorrectness,
model size or evidence quantity in isolation.
